# 第 6 篇（补充篇）· 摘要 / 半压 / 全压怎么放——一份具体的缓存摆放指南

> 本篇回答三个问题（都是读者真实反馈"没看懂"的点）：
> 1. **历史摘要**应该放在消息列表的哪里？为什么不能放 System？
> 2. **半压（层 2）** 的内容放在哪？
> 3. **全压（层 3）** 的内容放在哪？
> 4. 把项目里的东西按「稳定度」完整排个序。
>
> 阅读前提：知道"前缀缓存 = 从第一个字节开始比对，只要有一处不同，后面全部作废"。
> 所有注解以 **AI解析** 开头，用大白话讲。

## 0. 一页纸速览（先看结论，再看推导）

| 东西 | 最终"住"在哪 | 一句话 |
| - | - | - |
| 历史摘要 | **尾部材料块（turn-ctx）的开头** | 偶尔会变 → 住尾部安全区，绝不进 System |
| 半压（层 2） | **历史区原位，不搬家** | 位置不变，只换渲染形态（换衣服不换人） |
| 全压（层 3） | **列表里不存在了** | 整条删除；信息浓缩进摘要文本 |

```
请求的物理结构（发给模型时真实的样子）：

┌──────────────────────────────────────────────────────────┐
│ ① Sys（AGENT_SYSTEM，永远第一条，且全列表只有这一条）          │
│ ② 工具 schema（请求 tools 字段，属前缀区）                    │
├──────────────────────────────────────────────────────────┤
│ ③ 层 2 半压区   ← 半压住这（老历史：U 原文 + A' + Tool'）      │
│ ④ 层 1 原文区   ← 新历史住这（原文一字不动）                   │
├──────────────────────────────────────────────────────────┤
│ ⑤ 本轮用户问题 U_new                                        │
│ ⑥ turn-ctx 材料块 ← 摘要住这（块的开头！） + 证据 + 订单数据     │
│ ⑦ AI 思考 / 工具结果（ReAct 环内每一步追加）                   │
└──────────────────────────────────────────────────────────┘

层 3（全压）：不在图里——它从列表上消失了，信息变成了⑥开头摘要里的一句话。
```

## 1. 先把三个词钉死：原文 / 半压 / 全压

> **AI解析**：这三个词最容易混。它们**不是三个不同的仓库**，而是**同一条消息在三个不同"年龄段"的三种状态**：
>
> ```
> 新消息出生   →  变老，被"降级"  →  更老，被"摘要"
>   原文(层1)       半压(层2)           全压(层3)=删除
> ```
>
> 而且注意：**原件永远不会被销毁**。State.messages 里（以及 MySQL 里）全量历史一直躺着，
> 变的只是"每次调模型前，现拼出来的那份精简版长什么样"。用 JPA 打个比方——
> 数据库实体不动，每次查询动态拼一个 DTO 投影（projection）发给模型。

### 拿同一条 AI 答复看它的三种命运

**原文（层 1）** —— 一个字节不改，原样进请求：

```
满 99 元包邮哦！具体来说：普通地区满 99 元包邮，偏远地区（新疆、西藏等）
需满 199 元。另外会员还有免运费权益，可以在"我的-会员中心"查看。
如果超重还会加收续重费，具体以结算页为准。[1]
```

**半压（层 2）** —— 还在列表里，但换了渲染形态（[memory.py](../app/core/memory.py) `compress_reply`：

```python
def compress_reply(text: str, keep_chars: int | None = None) -> str:
    """客服答复降到层 2 的形态:留头部。客服答复第一句通常就是结论。"""
    n = settings.layer2_reply_keep_chars if keep_chars is None else keep_chars
    if not text or len(text) <= n:
        return text
    return text[:n] + "…(略)"
```

渲染结果（`layer2_reply_keep_chars` 默认 60）：

```
满 99 元包邮哦！具体来说：普通地区满 99 元包邮，偏远地区（新疆、西藏等）需满 199 元。另外会员还有…(略)
```

**全压（层 3）** —— 列表里没有它了。它的信息被大模型浓缩成摘要段里的一句话：

```
…用户曾询问运费规则，已告知：普通地区满 99 元包邮、偏远地区满 199 元、会员有免运费权益。
```

> **AI解析**：三条形态的"信息保真度"逐级下降：原文 100% → 半压 只留"结论句"（客服答复第一句通常就是结论）→ 全压 只剩转述。
> 为什么要这样？因为窗口装不下。**做减法是必然的，问题只是"减谁、什么时候减、减完怎么摆"**——本篇讲的就是"摆"。

## 2. 一条消息的"年龄轨迹"：看懂这张图就懂一半

> **AI解析**：每个时刻，系统里同一批消息被两个"锚点"切成三段。锚点是两个数字（消息 id），存在数据库里：
>
> - `summary_upto_msg_id`：**全压线**。id 小于它的 → 已进摘要，不出现
> - `layer1_from_msg_id`：**半压线**。两条线之间 → 半压；线之后 → 原文

```
全量历史（State.messages 里永远都在）：
┌──────────┬─────────────────┬──────────────────────┐
│ 全压区     │ 半压区           │ 原文区                 │
│ id ≤ 线1  │ 线1 < id ≤ 线2   │ id > 线2              │
└──────────┴─────────────────┴──────────────────────┘
       │            │                    │
       │            │                    │
       ▼            ▼                    ▼
  不出现(删除)   渲染成半压形态        渲染成原文
       │            │                    │
       └──── 它们的要点变成了"摘要段"文本，住在尾部 turn-ctx 块的开头 ────┘
```

> **AI解析**：注意"降级"是一个**批量动作**：
>
> - 层 1 超预算 → 半压线往前挪一批（原文变半压）；
> - 层 2 超预算 → 全压线往前挪一批（半压变删除）+ 生成一段新摘要。
>
> 而且项目刻意让锚点"**一次挪到位，两次之间不动**"（[memory.py](../app/core/memory.py) `next_layer1_from`：
> "从最新往回累加，累到预算为止"；[repository.py](../app/db/repository.py) `update_layer1_from`：
> "只在超预算时挪一次，两次之间不动——边界稳，渲染才逐字节稳"）。
> 为什么？**边界每轮微调 = 每轮都有字节变化 = 每轮都断链**。一次挪到位 = 一次断链，之后几十轮全命中。这就是"变化批量化"原则。

## 3. 逐问回答"怎么放"

### 3.1 历史摘要怎么放？——放尾部材料块的开头

**放法**：摘要文本是 `turn-ctx` 块的**第一段**，后面才是证据、订单数据。

看 [nodes.py](../app/graph/nodes.py) 里真实的拼装代码：

```python
def _turn_context(state) -> str:
    """本轮才有的材料:检索证据 + 退款路的订单数据。没有就返回空串。"""
    parts = []
    ss = memory.summary_system(state.get("summary"))
    if ss is not None:
        parts.append("\n\n" + ss.content)     # 摘要排最前:它讲的是更早发生的事
    if state.get("evidence"):
        parts.append(_KNOWLEDGE_EVIDENCE_HINT + state["evidence"])
    if state.get("route") == "refund_flow":
        parts.append(REFUND_JUDGE_HINT + json.dumps(state.get("order_data", {}), ensure_ascii=False))
    return "".join(parts)
```

而 turn-ctx 整条消息的位置，由 `_with_turn_context` 决定——插在**滑窗里最后一条用户消息之后**：

```python
def _with_turn_context(window: list, turn_ctx: str) -> list:
    """把本轮材料插在滑窗里最后一条用户消息之后。"""
    msg = HumanMessage(turn_ctx, id=TURN_CTX_ID)
    for i in range(len(window) - 1, -1, -1):
        if isinstance(window[i], HumanMessage):
            return [*window[:i + 1], msg, *window[i + 1:]]
    return [*window, msg]
```

最终列表长这样：

```
[Sys] [层2…] [层1…] [U_本轮] [turn-ctx: 摘要 + 证据 + 订单] [AI 思考] [Tool] …
                      ▲                                    ▲
                      本轮用户问题                          摘要住这（块的第一个）
```

**为什么绝对不能放 System（单独占第 2 条 SystemMessage）？**

> **AI解析**：这是全项目最贵的教训之一。看 [memory.py](../app/core/memory.py) `summary_system` 的注释：
>
> ```python
> """把摘要包成带标题的文本块;无摘要 None。
>
> 返回的是 SystemMessage,但调用点只取它的 .content,并进本轮材料那条 HumanMessage
> (见 nodes._turn_context)。整条消息列表里只允许有一条 SystemMessage,摘要单独占一条
> 会把工具定义挤到可变内容之后,前缀缓存整段作废 —— 实测命中直接归零。"""
> ```
>
> 展开讲：上游的 chat template 会把消息列表里**所有 system 消息上提、合并成一个头部块**。
> 所以"摘要单独放第二条 system" = 摘要被拼到 AGENT_SYSTEM 的屁股后面，而**工具 schema 本来是紧跟着 system 的**，现在被摘要这个"可变内容"挤到了后面：
>
> ```
> 错误摆法：[AGENT_SYSTEM][摘要(会变)][工具 schema][历史…]
>                                  ▲
>                          工具 schema 被挤到"会变的东西"之后 → 它后面的全不稳定
>
> 实测：无摘要的会话 cache_read=2048；摘要一进 system，cache_read 掉到 0。
> ```
>
> 这就是"**偶尔会变的东西，绝不能侵入铁打前缀区**"的活教材。

**为什么放尾部是正确的？先算清"材料块"的两笔账——它跨轮不指望命中（每轮全价），赚的是同轮命中 + 保护别人的命中。**

> **AI解析（跨轮的账）**：每轮结束，"上一轮 AI 回复 + 新问题"都会追加进历史；于是下一轮拼装时，
> 材料块前面会多出新内容，它在请求里的"位置"被整体错开：
>
> ```
> 第 N 轮：  [Sys][历史区][U_N][材料]
> 第 N+1 轮：[Sys][历史区][U_N][A_N][U_N+1][材料']
>             └──────── 命中 ────────┘└──── 断点之后全重算 ────┘
> ```
>
> 前缀匹配只认"从头连续相同"——材料块即使内容没变，也已经被 A_N、U_N+1 错开了位置 → **跨轮必然重算**；
> 何况证据本来就每轮必换。所以材料块从设计上就不指望跨轮命中——它是预算表里预留好的**固定开销**
> （摘要 3 段 + 证据 top_k×160 都是按"每轮重付"预留的）。
> 而同一张图里：A_N、U_N+1 这一轮是新内容（首轮全价），**从下一轮起沉入历史区、此后永久命中**——
> 复利在历史区，不在材料块。
>
> **AI解析（同轮的账）**：材料块真正赚命中的地方，是同一轮内的 ReAct 多步之间：
>
> ```
> 步 1：[Sys][历史区][U_N][材料]
> 步 2：[Sys][历史区][U_N][材料][AI1][Tool1]    ← 步 1 的整段是步 2 的前缀
> ```
>
> 材料（含摘要）在步 2、步 3……持续命中——这正是 `_with_turn_context` 把材料插在
> "用户问题之后、AI 第一步之前"、而不是列表最尾的原因（插最尾的话，AI1、Tool1 这些
> 每步必变的内容会把材料挡在断点之后）。
>
> **所以"放尾部"图的是三条**：① **保护头部**（放 System 实测 2048→0，见上文）；
> ② **同轮命中**（如上图）；③ **搭便车**（证据反正每轮重算，摘要进块＝零额外成本）。
> 顺带说清：既然材料块跨轮横竖全算，"块内"的变化模式就不构成缓存问题——
> 摘要"只追加不改写"的价值主要在**信息保真**（下一节）；
> 而"只带最近 3 段、证据限量"这类做法，是把这笔每轮固定开销**控小**的手段。

**为什么段落"只追加不改写"？** [repository.py](../app/db/repository.py)：

```python
async def append_summary_segment(conversation_id: int, from_msg_id: int,
                                 upto_msg_id: int, content: str) -> int:
    """追加一段摘要,同时把 conversations 的边界和拼好的投影一起更新。

    段落只追加不改写:已有的段不会再进模型,里面的订单号这类事实压过一次就定死了。
    conversations.summary 存的是最近若干段拼好的结果,读的时候少一次查询。"""
```

> **AI解析**：旧段一旦生成、永不重写——核心目的是**信息保真**：订单号这类事实只被压一次，
> 不会在反复"重新总结全文"中被磨掉（这正是 summarizer 注释的原话）。
> 附带地，块内字节保持"旧段永远是前缀"的追加模式，滚动窗口的"挤出"成为可预期的有界事件。

### 3.2 半压怎么放？——不用"放"，住原位，只换衣服

**答案：半压不在新的位置，它就待在历史区里自己原来的位置。** 项目做的是"改形态、不改位置"。

看清这个容易误解的点，[memory.py](../app/core/memory.py) `build_window` 注释原话：

```python
"""按两个锚点把历史渲染成三段:
  id ≤ summary_upto_msg_id            已进摘要,不出现在窗口里
  summary_upto < id ≤ layer1_from     层 2,渲染成半压形态
  id > layer1_from                    层 1,原样

锚点缺失(旧会话)或为 0 时那一刀不切,行为退化成单层原文 + token 兜底裁剪。
消息本身不动,变的只是渲染方式,所以同一份输入渲染多少次结果都一样。
只在调模型前现拼,不改 State。"""
```

> **AI解析**："消息本身不动，变的只是渲染方式"——把这句话读三遍。半压**不是**把消息搬到别的地方去，
> 而是：**同样是这批消息，在同一个位置上，每次渲染给模型时输出不同的形态**。
> 好比 JPA 里实体没动，只是这次查询把 DTO 映射规则换成了"精简版 mapper"。
>
> 而且这有三大好处：
> 1. **原件安全**：State.messages 里永远是原话，任何时候可以切回原文渲染；
> 2. **纯函数**：`to_layer2` 同样输入必得同样输出——锚点不动，渲染逐字节稳定（这是它敢待在历史区、
>    享受"中部稳定"待遇的资格）；
> 3. **可测试**：不用动数据库，一个纯函数就能单测三种形态。

半压区的三条"换装规则"（[memory.py](../app/core/memory.py) `to_layer2`）：

```python
def to_layer2(messages: list[BaseMessage]) -> list[BaseMessage]:
    """把一批消息渲染成层 2 形态。纯函数:同一批消息进来,结果恒定,重算多少次都一样。"""
    out: list[BaseMessage] = []
    for m in messages:
        if isinstance(m, HumanMessage):
            out.append(m)                      # 用户原话一字不动
        elif isinstance(m, AIMessage):
            # tool_calls 必须原样带上:……压的是正文,不是这一轮的调用结构。
            text = m.content if isinstance(m.content, str) else ""
            out.append(AIMessage(compress_reply(text), id=m.id,
                                 tool_calls=list(m.tool_calls or [])))
        elif isinstance(m, ToolMessage):
            text = m.content if isinstance(m.content, str) else str(m.content)
            out.append(ToolMessage(
                compress_tool_result(getattr(m, "name", ""), text),
                tool_call_id=m.tool_call_id, name=getattr(m, "name", None), id=m.id))
        else:
            out.append(m)
    return out
```

| 消息类型 | 半压规则 | 为什么 |
| - | - | - |
| 用户原话 | **一字不动** | "那双跑鞋""订单 1001"这些指代线索全在用户话里 |
| AI 答复 | 留前 60 字 + `…(略)` | 客服答复第一句通常就是结论 |
| 工具结果（小，≤200 token） | 原样保留 | 订单字段下一轮追问还用得上 |
| 工具结果（大） | 压成 `(已调用 xx,结果从略)` | 检索证据是"一轮用的一次性材料"，答完就不该再占位 |
| tool_calls 结构 | **必须原样带** | 漏了上游直接 400（tool result's tool id not found） |

半压的"变化时刻"只有一个：**降级**（层 1 超预算时，一批最老的原文变半压）。

> **AI解析**：这一刻，那批消息的字节形态变了（从原文变半压）→ 从**这批消息的第一个位置**起，缓存断链一次。
> 但仅此一次——锚点"一次挪到位"，之后几十轮不动，半压区又逐字节稳定。
> 所以半压区的稳定度定级是"**次稳定（中部）**"：平时稳如磐石，降级时付一次账单。

#### 3.2.1 读者追问：半压区为什么排在原文区前面？它变了不是先断吗？

> 这是读者真实提出来的疑问："半压会变化，为什么不把更稳定的原文放前面？"三条讲透。

**第一，半压不会"每轮变化"——它是"冻住的形态"，不是"持续压缩的过程"。**

> **AI解析**：半压区和原文区一样，是"锚点 + 纯函数"双重保证下的**逐字节稳定**内容：
> `to_layer2` 是纯函数（同一批消息进、同样字节出）；锚点规则是"一次挪到位、两次之间不动"。
> "压缩动作"只发生在**降级那一刻**——一批原文被划进半压区，压一次，然后**冻住**，
> 此后几十轮每次渲染的字节完全一致。所以两者在稳定度上是**同级**的（排序表里同为"次稳定·中部"），
> 不存在"谁更该放前面"的排序问题。

**第二，顺序不是"缓存摆放"选出来的，是对话时间轴本身。**

> **AI解析**：消息列表首先是"聊天记录"——U1 必须在 U2 前面，打乱顺序模型就读不懂上下文，
> 这是**语义硬约束**，缓存优化只能在约束内做。而压缩的方向是固定的：**永远先压最老的消息**
> （对当前问题价值最低）。于是"已压缩区（半压）"必然出现在"未压缩区（原文）"的左边，
> 像一根从老往新推进的水位线：
>
> ```
> 老 ──────────────────────────────► 新
> [全压(删)][半压区][原文区][本轮问题][材料]
>            ▲
>          压缩水位线：从老往新推进
> ```
>
> 类比：日志滚动（logback 的 RollingFileAppender）、数据库冷热分层——归档永远从最老的开始，
> 冷数据（已压缩）在左、热数据（未压缩）在右。这不是摆放选择，是"压缩从哪头开始"的必然结果。

**第三，降级那一刻的账躲不掉——但它与"谁放前"无关。**

> **AI解析**：降级时缓存确实断链一次，但这笔账**无论怎么排序都要付**，因为**断点位置由
> "哪批消息被处理"决定**，不由区域顺序决定：压缩的是最老批次 → 断点就在中段靠前。
> 假设强行把原文区搬到半压区前面（先不说违反对话语义根本不可行）——降级时断点照样出现在
> "被压批次的位置"，一分钱省不下来。
>
> 项目的对策不是"消除断点"，而是：**低频 + 批量 + 一次付清**（锚点一次挪到位）。
> 一个精确细节：降级时真正的断点是"**新划入批次的起点**"——它**前面**的老半压内容仍然全部命中；
> 而且随着会话推进，每次降级的批次越来越新，断点逐次后移，账单越付越小（第一次降级最贵）。

#### 3.2.2 连续两次降级：第二次压谁？老半压还在吗？

> 读者场景："对话 1,2,3,4,5,6,7，第一次半压压了 1,2,3，到 6 又要半压时压哪里？原来的 1,2,3 还放请求里吗？"

**答案：第二次压的是"上次分界线之后那批原文里最老的"（例子里的 4，可能带上 5）；1,2,3 一个字节都没动，原位原样继续放。**

机制三句话（[runtime.py](../app/graph/runtime.py) `settle_layers` + [memory.py](../app/core/memory.py) `next_layer1_from`）：

1. **轮末结算**：每轮结束时量一下层 1 的实际 token，超过预算（`sliding × 0.7`）才动手，纯计算、不调模型；
2. **重算分界线**：`next_layer1_from` 从**最新往回**逐条累加，累到超预算处，把边界落在"这之前最近的一条用户消息"上——新边界是"从最新倒推"算出来的，不是"接着上次往后挪一点"；
3. **只进不退**：`if new_from > layer1_from` 才更新——分界线**只往后挪、永不回退**。结果：半压区**只扩张、不换人、不重压**。

```
第一次降级（走到 4 时，层 1 超预算）：
[1][2][3] | [4]              分界线 3|4
 半压(新划入)   原文

第二次降级（走到 6 时，层 1 又超）：
[1][2][3] [4][5] | [6][7]    分界线从 3|4 挪到 5|6
 └─没重压、没挪动─┘ └本次新划入┘  原文
```

> **AI解析**：1,2,3 为什么能"一动不动"？两个保证——渲染侧，`to_layer2` 纯函数，锚点没让它们换区，每次渲染字节相同；
> 锚点侧，分界线单调后移，它们永远落在"已半压"区间里。
> 这就是缓存账最划算的部分：第二次降级的断点 = **新划入批次的起点**（4 的起点），断点之前（Sys + 1,2,3 的半压）全部照常命中。
> 反过来说：如果每次降级都把老消息"重新压一遍"，断点会回到列表更早处，白付一次大账单——项目绝不干这事。

**那 1,2,3 什么时候才从请求里消失？——全压（摘要）时"一锅端"。**

> **AI解析**：全压的判据是**整个半压区**超预算（层 2 token > `sliding × 0.3`，
> [summarizer.py](../app/core/summarizer.py) `_should_summarize`："压缩是成本不是美德，装得下就别压"）。
> 触发后 `run_summary` 把**当时整个半压区**（`summary_upto` 到 `layer1_from` 之间的所有消息——例子里的 1,2,3,4,5……**全部**）
> 打包送给模型，压成**一段新摘要**；完成后 `summary_upto_msg_id` 后移到当时的 `layer1_from`
> → **半压区清空**，1,2,3 从此不再出现在请求里（要点在摘要段里续命，住 turn-ctx 开头）。
>
> 一句话总结：**半压是"一批一批划进来、只进不出"；全压是"攒够了整锅端走、清空重来"。**
> 顺带一个边界提醒：全压"一锅端"时删的是列表前中段，断点会回到靠近 Sys 的位置（单次账单最大）——
> 所以它做得非常克制，只在层 2 超预算时才出手。

### 3.3 全压怎么放？——没有位置，它是"删除"

**答案：全压内容不"放"在任何地方——它从发给模型的列表里整个消失了。**

- 窗口渲染层面：`id ≤ summary_upto_msg_id` 的消息**不出现**（[memory.py](../app/core/memory.py) `build_window` 第一刀）；
- 信息层面：它的要点被大模型浓缩进**摘要段文本**，位置 = turn-ctx 块的开头（见 3.1）；
- 数据层面：原件还在 State.messages 和 MySQL 里，一条没丢。

**全压的"变化时刻"**：摘要生成时（层 2 超预算触发）：

> **AI解析**：这一刻发生了两件事——
> 1. **整个半压区**（当时所有半压消息"一锅端"）从"窗口"里消失（列表中部少了一截）；
> 完成后 `summary_upto_msg_id` 后移到当时的 `layer1_from`，半压区清空、重新开始积累；
> 2. 摘要段追加/挤出（尾部块变化）。
>
> 缓存断链一次。但仍然符合"变化批量化"：不是每轮删一点，而是攒够了删一批、摘要一次生成、锚点一次到位。

**全压"删"得心不心疼？** 不心疼，三层保险：

| 保险 | 说明 |
| - | - |
| 关键事实进摘要 | 且"压过一次就定死"（append_summary_segment 注释原话） |
| 原件还在库里 | State.messages / MySQL 全量保留，任何时候可查 |
| 数据可重查 | 工具类数据"下次实时查，比留着的旧值还新"（compress_tool_result 注释） |

## 4. 完整稳定度排序表（含"变了会怎样"）

> **AI解析**：排序的根据有两个，缺一不可：
> ① **变化频率**（多久变一次）；② **变化波及面**（它一变，后面多少内容作废——越靠前波及越大）。
> 频率低 + 放得靠前 = 复利；频率高 + 放得靠后 = 损害可控。

| # | 元素 | 请求里的位置 | 什么时候变 | 定级 | 变了会怎样 |
| - | - | - | - | - | - |
| 1 | Sys（AGENT_SYSTEM） | 第 1 条 | 代码发布 | 铁打前缀 | 全部断链（灾难级） |
| 2 | 工具 schema | 请求 tools 字段（前缀区） | 发布 / MCP 故障 | 铁打前缀 | 全部断链（灾难级） |
| 3 | 摘要文本 | turn-ctx 块开头 | 全压时追加新段（挤出罕见） | 偶变·尾部 | 材料块本就每轮重算，不叠加额外损失 |
| 4 | 半压区（层 2） | 历史区前段（原位） | 降级时（批量） | 次稳定·中部 | 从该批消息位置起断一次 |
| 5 | 原文区（层 1） | 历史区后段 | 降级时（批量） | 次稳定·中部 | 从该批消息位置起断一次 |
| 6 | 全压内容（层 3） | **不存在** | 生成摘要时被删 | — | 信息在摘要里续命 |
| 7 | 本轮用户问题 | 尾部（历史区后） | 每轮新 | 必变·尾部 | 不心疼（本来就该变） |
| 8 | 本轮材料（证据/订单数据） | turn-ctx 块 | 每轮必变 | 必变·尾部 | 不心疼 |
| 9 | AI 思考（含 tool_calls） | ReAct 环尾部 | 每步新 | 必变·最尾 | 不心疼 |
| 10 | 工具结果 | ReAct 环尾部 | 每步新 | 必变·最尾 | 不心疼 |

> **AI解析**：把这张表和 3.1/3.2/3.3 串起来看，规则其实只有一句话——
> **"铁打前缀放最前，老历史放中间（要动一次动一批），摘要住尾部块的头部，每轮必变的全塞最后。"**
>
> 之前读者容易困惑的一点，这里特别澄清：**"放哪"不是按"内容的新旧"分的，而是按"字节的稳定度"分的**。
> 摘要讲的是历史，但它"偶尔会变"，所以没资格住历史区（历史区的入住条件是"旧字节永不变"），
> 只能住尾部的安全区。半压和原文是"老历史"，但形态一旦确定就逐字节稳定，所以能安心中部。
>
> 另外把"尾部"这一档再拆细：第 7、8 行都是"每轮必变"，但命运不同——
> **新消息（用户问题、AI 回复）首轮全价、从下一轮起沉入历史区、此后永久命中**；
> **材料块（摘要+证据）永远每轮重算**。这就是"复利在历史区、材料靠同轮"的完整版。

## 5. 三条傻瓜判定法（拿到任何内容都能自己判断）

> **AI解析**：以后你设计自己的 Agent，遇到"这段东西放哪"，问三个问题：
>
> **问题一：它多久变一次？**
> 一次不变（发布才变）→ 往前放；偶尔变（攒够一批才变）→ 中间或尾部的头部；每轮/每步都变 → 往后放。
>
> **问题二：它变了，会让"它后面"多少内容作废？**
> 前缀缓存的杀伤规则是"从变化点往后全废"。所以**越易变的越靠后**——
> 它变化时，后面已经没有（或很少）内容可以陪葬了。
>
> **问题三：它必须变的时候，能不能批量、一次到位？**
> 能批量的绝不要微调：锚点"一次挪到位"（layer1_from）、摘要"批量生成且不改写"、
> 工具顺序"三层保险"。批量 = 账单只付一次；微调 = 每轮都付。

## 7. FAQ：把最容易混的六个点讲透

**Q1：摘要讲的是"历史"，为什么不放历史区（和半压/原文一起），而要放尾部？**

> A：历史区的"入住资格"是"**旧字节永不变**"——这是把它放前面的底气。摘要的"最近 N 段"窗口
> 偶尔会滚动（挤出一段），不够格。所以它只能住"尾部的安全区"。**住哪由稳定度决定，不由内容新旧决定。**

**Q2：半压消息的字节会变吗？**

> A：两层含义分开看——① 单条消息的形态：不变（纯函数渲染，锚点不动则逐字节一致）；
> ② 成员资格：会变——"降级"时刻一批原文被划进半压区，从这批消息的位置起断链一次。
> 这就是"次稳定"的含义：平时稳，动起来只动一次。

**Q3：全压（删除）了，信息不就丢了吗？**

> A：三层保险。① 关键事实已进摘要（且"压过一次就定死"）；② 原件在 State.messages / MySQL 里
> 全量保留；③ 工具类数据可以实时重查——"比留着的旧值还新"。

**Q4："老历史放中间"和"摘要也是老历史却放尾部"，矛盾吗？**

> A：不矛盾。前面说了：**按字节稳定度分，不按内容新旧分**。老历史（U/A/Tool 消息）一旦生成，
> 字节就固定了（除非降级）；摘要文本的窗口偶尔滚动。稳定度不同 → 住所不同。

**Q5：工具 schema 是每轮现拉的（动态），为什么算"铁打前缀"？**

> A：机制动态 ≠ 内容每轮不同。"每轮现拉"是保险动作，拉回来的内容 99.9% 的轮次一模一样；
> 真变化（MCP 故障/热更）是罕见事件，接受"一次性断链"。且项目用三层保险保证"同一工具集时
> 顺序逐字节稳定"（`registry.get_all_specs` 注释详解）。详见第 3 篇/前文"工具顺序"一节。

**Q6：每轮请求都会追加上一轮 AI 回复，历史摘要放在后面，不就被新消息挤得命中不了吗？**

> A：观察对了一半——**材料块（含摘要）跨轮确实每轮重算、不命中**。但这不是失误，是合意设计：
> ① **它没得选**：它前面每轮都会长出新内容（上一轮回复、新问题），位置必然被错开；
> ② **它不靠这个**：真正的复利在历史区——上一轮的回复和新问题首轮全价，从下一轮起沉入历史区、永久命中；
> ③ **它的收益在别处**：同轮 ReAct 多步之间整段命中（步 1 是步 2 的前缀），且"放尾部"保护了
> 头部与历史区的命中（放 System 实测 2048→0）。
> 加上证据本来就每轮必换（固定开销已预算），摘要搭车重算＝零额外成本。详见 3.1 的"两笔账"。

## 8. 一页纸总结

```
┌──────────────────────────── 请求的固定结构 ────────────────────────────┐
│ ①Sys + ②工具 schema ─────────── 铁打前缀（发布才变，永不人为抖动）        │
├──────────────────────────────────────────────────────────────────────┤
│ ③半压区（老历史，原位换装）──┐                                          │
│ ④原文区（新历史，一字不动）──┴─ 次稳定中部：降级时批量断一次，之后逐字节稳   │
├──────────────────────────────────────────────────────────────────────┤
│ ⑤U_本轮                                                              │
│ ⑥turn-ctx：摘要住块首（跨轮每轮重算；同轮多步命中）+ 证据 + 订单            │
│ ⑦AI 思考 / 工具结果（ReAct 环，每步追加）                                │
└──────────────────────────────────────────────────────────────────────┘

口诀：
  铁打前缀放最前；老历史放中间、要动一次动一批；
  摘要住尾部块的头部；每轮必变的全塞最后。
  判定三问：多久变一次？变了波及多少？能不能批量一次到位？
```

> **AI解析**：最后一句大白话收尾——
> **"放在前面的东西，赌的是它一辈子不变；放在后面的东西，认的是它随时会变。
> 所以你要做的就是把每个东西诚实归位：稳定的往前放（吃复利），易变的往后放（断也断得便宜），
> 偶尔变的让它批量变（一账单就完事）。"**
